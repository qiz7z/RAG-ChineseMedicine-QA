## 二、起点：旧口径为什么虚高（已定量拆解）

README 长期对外的 `94%/91%` 是 **loose 口径**，有三重放大：

| # | 放大源 | 量级 |
|---|--------|------|
| 1 | **完全不判章节**——`loose = drug_match_loose(...)`，只看药品名子串。问「人参的性味归经」，只要 top-5 出现**任意**一条人参 chunk（哪怕内容是【含量测定】）就算命中 | 30 道判命中里 **27 道章节是错的** |
| 2 | **11 题 `expected_drugs=[]` 无条件命中**（**已于同日收口**：标 `out_of_scope` 后两项口径都不计分）；其中 **10 道「方法通则」题考的是药典四部，而语料只有一部——源里根本没有答案** | 白送 **11pp** |
| 3 | **双向子串**匹配：期望「黄连」，检索到「黄连**胶囊**」也算命中 | `drug_not_exact = 3` |

**另一条独立铁证**：loose 的首次命中 **91/94 落在第 1 位**。因为药名解析后会做元数据过滤，
第 1 位必然是该药品 —— 也就是说，**这个指标实际衡量的是「查询解析器有没有抽出药名」，
而不是「检索有没有找到答案」**。README 表里 `Hit@1 = Hit@3 = Hit@5 = 91%`、`MRR = 0.9100`
四个数完全相等，就是这现象的直接体现。

> 需要说明：`src/eval/evaluator.py` 的注释**明确写了** loose 的两个放大器，原话是
> 「保留口径是为了让三方可比，不是为了报高」，并且**主动实现了 strict 档**、
> 写了 `tests/test_eval_criteria.py` 对两份实现做对拍。工程上做得规范。
> 问题出在**对外叙述**——全文检索 `README.md`，`strict / 严格 / loose` **一个字都没出现**，
> strict 结果只躺在 `data/eval/reports/` 的 JSON 里没人看见。

## 三、11 个缺陷（按发现顺序）

| # | 缺陷 | 影响 | 修复位置 |
|---|------|------|---------|
| 1 | 横向查询分类过滤值不匹配：解析器返回简称 `"药材"`，元数据实际是 `"药材和饮片"` → 过滤恒不命中 | 手撕版横向查询**召回 0 条**（标准版早已修，**未回移**） | `src/retrieval/query_parser.py` |
| 2 | 章节信息被浪费：`parsed["sections"]` 解析出来却**从未用于检索** | `section_missing` 18 题，35% 失分源于此 | `src/retrieval/retriever.py` |
| 3 | 药品名扩展是**双向**的：查「双黄连口服液」会把「黄连」拉进过滤集 | 抵消最长匹配去重，top-1 落到黄连（语料 433 个条目受影响） | 两版各 2 处 |
| 4 | **langchain FAISS 的 `filter` 只作用于全局 top-20**（`fetch_k` 默认 20） | **标准版 strict 长期低 22pp 的真凶**；「枸杞子」6 个切片只召回 2 条 | `langchain_app/retrievers.py` |
| 5 | **ETL 丢弃表格形式的【处方】**：表格首格自带【章节】标记、紧跟拼音名之后（此时 `current_section` 为 None）→ 整表静默丢弃 | **530 个成方制剂的处方内容不在知识库**，其中 58 个还被误判为「药材和饮片」 | `src/etl/parser.py` |

| 7 | **ETL 跨药品串块 / 条目丢失**：① 药名+拼音+拉丁名挤在同一段落（软换行 `w:br`）→ 按整段判药名因超长被否决；② 药名用 `Body text\|3` 样式，被排除在 `EXTRA_DRUG_NAME_STYLES` 外 | **36 个药品条目整条丢失** + **31+ 处内容被追加进上一个药品** | `src/etl/parser.py` |
| 8 | **OCR 药名错字 / 异体字回流**：`川B`(芎)、`梔子`(栀)、`马齿免`(苋)、`豬签草`(豨薟草)、`幵胸顺气丸`(开)、`淫羊蕾`(藿)… | **167 个药名用户按正确写法搜不到**（首批 127 + 复查批 40）；正文 `梔` **8,892 次** | `src/etl/cleaner.py` |
| 9 | **章节提升缺「药名精确度」排序键**：查询药名扩展是**子串**方向，含该药名的成药会把正主挤下去 | 修名后 `炙黄芪`/`黄芪颗粒` 压过 `黄芪-饮片`，**8 道黄芪题的 strict@1 一起下降** | 两版 `retrievers` |
| 10 | **药名清洗的两个系统性缺陷**：① 只 `replace(' ','')`，去不掉 docx 的 **`<w:tab/>`**，而随后的 `clean_text` 会把 Tab **折叠成空格** → 库里落成 `策 巨`；② **规则键与清洗顺序错配**——`fix_drug_name` 先跑、`蔥→蒽` 在 `clean_text` 里后跑，键写成 `蒽麻子` 就永远命中不了 | 带空格的药名让精确匹配失效；1 个药名（`蒽麻子`）规则空转 | `src/etl/cleaner.py::clean_entry` |

## 五、⚠️ 哪些改动 `Hit@K` 根本看不见（最重要的方法论）

这是本轮最该记住的一条。**这个评测集对「实现细节类 / 数据质量类」改动是盲的**，四个实例：

| 改动 | 指标变化 | 真实影响 |
|------|---------|---------|
| 缺陷 3（双向扩展） | 修复前后 **0/106** 题差异 | 语料 433 个条目受影响，只是没有题目的期望药名包含另一药名 |
| 分类判定重构（41 条） | 精确到小数点后**完全相同** | 逐题仅 **1/106** 变化，还是不可评测题 |
| 缺陷 6（标点假阴性） | 检索指标**无变化** | 生成侧覆盖率低估 7.5pp |
| 缺陷 7（串块，36 个药品） | 两版**反向**各动 ~1pp（src −1.05 / lc +1.06） | 36 个药品从不可检索变可检索；31+ 处污染上下文被清除 |

**结论**：这类改动不要看 `Hit@K`，要写**不变量断言**。所以 `tests/test_retrieval_fixes.py`
断言的是「候选集里不得出现单向扩展出来的短药名」「章节信息必须参与排序」这类性质，
而不是分数。

反过来，本轮**唯一指标明显可测**的是缺陷 8 + 9（OCR 药名与排序键）——
它直接决定检索能否命中，单题证据清清楚楚：

```
Q006「川芎的性味归经」        修复前 top1 = 川楝子 / 冬虫夏草（错） → 修复后 = 川芎（对）
Q031「川芎的性状和功能主治」   修复前 top1 = 醒脑再造胶囊（错）    → 修复后 = 川芎（对）
```

## 七、最值得记住的 7 个坑

1. **langchain 的 `filter` 是「先取全局 top-20 再套 filter」**（`fetch_k` 默认 20）。
   目标药品不在全局 top-20 就整批丢失 → 显式传 `fetch_k = index.ntotal`。
2. **ETL 的两处静默丢弃**：表格首格带【章节】标记时整表被丢（缺陷 5）；
   Word 软换行 `w:br` 让药名与拼音同段导致药名被否决（缺陷 7）。**两者都是静默的**，
   不报错、不掉日志 —— 只能靠「数据规模对不上」和「抽查到的脏名字」发现。
3. **同一个错字在药名与正文里的合法性可以完全不同**：`茂` 在正文合法（140 次「叶茂盛时采收」）、
   `苔` 合法（「苦苣苔科」）、`蕾` 合法（「干燥花蕾」）、`萼` 合法（「萼筒」）、`替` 合法（「被替代对照品」）。
   整字替换**只能用于药名**，正文必须走词组级。
4. **「看起来像 OCR 错」不等于「只有一个正确写法」**：`醍` 同时是 乙醚(1485)/石油醚(695)/蒽醌(41)，
   `豬` 全是 豨 而「猪」另正确出现 303 次，`蔥` 全是 蒽。整字替换前**必须看全库上下文分布**。
5. **别用 `zhconv` 整库转繁简**：《药典》里 `癥`（化癥回生片）是**正确**用法，会被错改成「症」。
6. **单一信号一定筛不干净，要用第二个独立信号交叉验证**。首轮用"字符在正文出现次数"粗筛出 127 个；
   复查改用「`pinyin_name` vs `pypinyin` 标音」又找出 **40 个** —— 前者的漏网原因是错字在正文里有
   别的合法用法。**而第二个信号本身也会错**（见下条）。
7. **只用拼音判定会出错，必须用拉丁名/概述二次确认**：`S草` 拼音 `Shicao`，
   据此判成「茜草」是**错的**——拉丁名 `ACHILLEAE HERBA` + 概述「菊科植物**蓍**」证明是 **蓍草**，
   而真「茜草」是另一条（拉丁 `RUBIAE RADIX`）。标错后库里会冒出两个「茜草」。
   另一面：**规则键必须用「原文形态」的字**——`fix_drug_name`（药名层）跑在 `clean_text`（正文层）
   **之前**，所以键写成清洗后的 `蒽麻子` 就永远命中不了原文的 `蔥麻子`。

> 补充一条工程教训：**改动后要验证"落盘"**。本次有 3 次编辑
> （README×2、MEMORY×1）工具报告成功但内容未持久化，靠 grep 复查才发现并重做。

| 回答准确率 ≥ 95% | **项目里没有「准确率」指标**。关键词覆盖率 79.90% 只是召回倾向；新增的**论断有据率 90.55%** 是最接近的替代 | **仍未达标**。论断有据率衡量"说的有没有依据"，不等于"答得对不对"；真正的准确率需要人工标注或参考答案比对 |
| 幻觉率 ≤ 3% | **LLM-as-judge 实测 11.72%**（无据 9.52% + 矛盾 2.20%，去污染分母） | **未达标**，超过目标 3 倍。旧的「数值一致性检出 10.09%」只是幻觉率**下界**，不能拿来对标 |

长期被当作成绩展示、实际不成立的指标：

- **「引用率 100%」是恒真指标**——`langchain_app/postprocess.py` 直接把 citations 从检索结果的
  metadata 拼出来，只要检索有结果就必然有引用，跟回答质量无关。
  已由**论断有据率 88.28%** 取代。
- **横向条件查询 56%** 是相对短板，且**评测侧口径本身不适配**：该类型的 `expected_drugs`
  是**集合**（如「哪些药材含挥发油」=[人参,黄芪,白术,甘草]），用「命中任一药品」判分本就不合理。
