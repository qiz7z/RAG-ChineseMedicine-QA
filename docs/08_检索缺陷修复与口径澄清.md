> 后续又修了缺陷 7（ETL 串块/条目丢失）、8（OCR 药名/异体字）、9（药名精确度排序键），

> 结论：**是，但原因一半在口径、一半在真实缺陷**。本文记录口径澄清、找到并修掉的 4 个检索缺陷、

## 一、口径澄清：Hit@5 = 94% 是什么口径

项目长期对外宣称的 `Hit@5 = 94%`（标准版）/ `91%`（手撕版）来自 **loose 口径**，它有三个放大源：

| # | 放大源 | 代码位置 | 影响 |
|---|--------|---------|------|
| 1 | **完全不判章节**。只判 `drug_name` 双向子串匹配，`expected_sections` 传进去了但从未参与判定 | `src/eval/evaluator.py::judge_result`（`loose = drug_match_loose(...)`） | 问"人参的性味归经"，只要 top-5 里有**任何一条**人参的 chunk（哪怕是【含量测定】）就算命中 |
| 2 | **11 题无条件判命中**（`expected_drugs` 为空） | `drug_match_loose` 首行 `if not expected_drugs: return True` | 白送 11 个百分点 |
| 3 | **双向子串**：期望"黄连"，检索到"黄连**胶囊**"也算命中 | `any(e in d or d in e ...)` | 成方制剂被算成药材命中 |

其中第 2 条最直接：那 11 题里有 **10 道"方法通则查询"问的是药典四部通则正文**（薄层色谱法、水分测定法…），
而本系统只索引了**一部**——语料里只有"照薄层色谱法（通则0502）"这类引用、没有正文，
**数据源里根本没有答案**。README 分类型表却把这 10 题记为 **100% 命中**。

另一条独立证据说明 loose 指标接近恒真：**首次命中排名分布 91/94 落在第 1 位**。
因为查询解析出药名后会做元数据过滤（`drug_name $in`），第 1 位必然是该药品——
该指标实际衡量的是"查询解析器有没有抽出药名"，不是"检索有没有找到答案"。

### 现在的做法

`src/eval/evaluator.py` 与 `langchain_app/eval.py` **双口径并存**，报告并列输出：

- `retrieval` 块 = loose（保留以与历史报告可比，**不作为对外指标**）
- `strict_retrieval` 块 = strict（**对外引用用这一档**）

strict 判据：药品名**精确**匹配（含该药饮片条目，用 `category` + `is_yinpian` 卡掉成方制剂）
+ 期望章节必须在 chunk **正文**里真实出现（找 `【章节】` 标记）。
`expected_drugs` 为空的题不计入分母 → 分母 89 题。

> ⚠️ 判章节**不能**用 metadata 的 `section` 字段：那是 ETL 的合并桶名
> （`临床应用` = 【性味与归经】+【功能与主治】+【用法与用量】+【注意】+【贮藏】合并；
> `药品概要` = intro_text；`完整条目` = 整条拼接），与药典原生章节名不同源，
> 直接比对会大面积假阴性。

## 二、找到并修掉的 4 个检索缺陷

### 缺陷 1：横向查询分类过滤值不匹配（手撕版独有，影响最大）

`src/retrieval/query_parser.py::_detect_category_filter` 返回的是**简称** `"药材"` / `"成方制剂"`，
而 chunks 里 `category` 的**实际值**是 `"药材和饮片"` / `"成方制剂和单味制剂"` / `"植物油脂和提取物"`：

```
meta.get("category") != "药材"   # "药材和饮片" != "药材" → 恒 False
```

后果：横向条件查询的 category 过滤**恒不命中**，向量路和 BM25 路双双返回空 → **横向查询召回 0 条**。

> 该缺陷在标准版里早已修好（`langchain_app/query_understanding.py` 的 `CATEGORY_MAP`，
> 其 docstring 明写"修复了分类简称与实际值不匹配的缺陷"），但**从未回移到手撕版**。

**修复**：手撕版加同名 `CATEGORY_MAP` 并返回实际值。

### 缺陷 2：章节信息被解析出来却从未使用

`QueryParser.parse()` 一直会返回 `sections`（如"性味归经"→`性味与归经`），
但 `Retriever.search()` **只用它做了药品名过滤，章节信息直接丢弃**。
结果就是体感上的"药品召回对了、章节没进 top-5"——评测里归因为 `section_missing`。

**修复**：新增"章节感知召回"。在 RRF 候选集内，把正文含 `【目标章节】` 标记的 chunk 提前
（同命中数保持 RRF 原序，稳定排序）。判据与评测 strict 口径一致，不引入任何模型。
开关 `ENABLE_SECTION_BOOST`（默认开，可关闭做消融）。

### 缺陷 3：药品名扩展是双向的，会拉进更短的无关药名

```python
if fd in dn or dn in fd:      # ← 第二个方向是错的
    expanded_drugs.add(dn)
```

查"**双黄连口服液**"时，`"黄连" in "双黄连口服液"` 成立 → 把"黄连""黄连片"全拉进过滤集，
抵消了查询解析器已经做好的最长匹配去重，**top-1 直接落到黄连上**。

**修复**：改为单向（`fd in dn`，即"以查询药名为主体的变体"，如 人参 → 人参-饮片）。
两套引擎的向量路 + BM25 后过滤共 4 处，口径已统一。

### 缺陷 4：langchain FAISS 的 `filter` 只作用于全局 top-20（标准版独有，22pp 差距的真凶）

标准版 strict 长期比手撕版低 22pp，此前一直"异常待核"。根因在 langchain：

```python
# langchain_community/vectorstores/faiss.py
scores, indices = self.index.search(vector, k if filter is None else fetch_k)   # fetch_k 默认 20
```

即 langchain 的过滤是「**先按向量取全局 top-`fetch_k`（默认仅 20），再对结果套 filter**」。
目标药品的切片只要不在全局 top-20 里就会**整批丢失**。

实测：查"枸杞子的功能主治"，该药材有 6 个切片，却被限制成只召回 **2 条**，
且候选里**没有任何含【功能与主治】的 chunk**——章节召回也因此无从施展。
手撕版是自己搭过滤后的子集索引再检索，所以不存在这个问题。

**修复**：`search_kwargs` 显式传 `fetch_k = self.vectorstore.index.ntotal`，
语义上等价于"先过滤再检索"。`IndexFlatIP` 暴力扫描 11k×1024 仅数毫秒，代价可接受
（P50 从 0.059s → 0.093s）。

## 三、附带发现

- **51 个成方制剂被 ETL 误标为 `药材和饮片`**（九气拈痛丸、木香槟榔丸、保和丸、感冒清热颗粒、
  活血止痛散、壮骨关节丸…）。这会污染横向查询的"药材"过滤结果。修它需要动 ETL 的分类推断并重建索引。
- **测试集不覆盖反向子串场景**：缺陷 3 修前/修后逐题对比 **0/100 题受影响**——
  100 题里没有任何题目的期望药名包含另一个药名（如"双黄连口服液"含"黄连"）。
  即：这类 bug 靠现有评测集**测不出来**，只能靠人工探测发现。

  `蛤蛤定鬧丸`（喘）、`川B`（芎）、`炙红茂`（芪）等仍出现在对外服务的药品名里。

## 五、判分口径的另一处缺陷：生成侧关键词覆盖率

检索侧修完后复查生成侧，发现**同一类问题**（都是"判分比数据更严格/更死板"）。

`expected_answer_keywords` 把剂量范围写成**半角连字符**（`6-12g`、`10-15g`），
而药典原文用的是 `〜`（U+301C）。`kw in answer` 的子串匹配因此必然失配 → **答对的题被判 0 分**：

```
[Q003] 当归的用法用量是怎样的？
   期望关键词: ['煎服', '6-12g']
   回答      : "**用法与用量：6〜12g。**"     ← 答案本身是对的
   命中      : []                              ← 却判 0（'6-12g' 不是 '6〜12g' 的子串）
```

### 量化（在**同一批 LLM 回答**上只换判分，隔离模型波动）

| 引擎 | 旧口径 | 新口径 | 0 覆盖题 | 原本被判 0、实际答对 |
|------|--------|--------|----------|---------------------|
| 手撕版 | 67.10% | **74.43%** | 18 → 8 | Q003/Q008/Q013/Q017/Q024/Q047/Q049/Q050/Q055/Q098 |
| 标准版 | 64.43% | **72.27%** | 23 → 12 | 同上 + Q041 |

### 修复

两套判分实现各加一份 `normalize_text`（NFKC 折叠全角/半角 + 统一 7 种连字符
`〜～~–—－‑` + 去空白 + 小写），关键词匹配前先规范化。
新增 5 项回归测试，含**两版实现对拍**（`tests/test_eval_criteria.py::TestKeywordNormalization`）。

> 这印证了 README「后续优化方向」里早已写下的第 6 条——"当前关键词/子串判分对改写与全角标点敏感"。
> 问题一直被记录，但从未修。

**修正后重跑（2026-09-22，同通道 agnes-2.5-flash，100 题）**

| 引擎 | 关键词覆盖率 | 引用率 | 数值一致性检出 | P95 |
|------|-------------|--------|---------------|-----|
| 手撕版（8-30 → 9-22） | 58.6% → **72.77%** | 92% → 100% | 12% → 11% | 17.6s |
| 标准版（8-30 → 9-22） | 60.5% → **74.27%** | 100% | 13% → 12% | 22.6s |

> ⚠️ 覆盖率提升**不能全归功于本次修复**：口径修正约占 +7.5pp（已隔离测得），
> 其余来自检索变好（上下文含正确章节）与 LLM 日间波动，后两者未做受控分离。
> **「引用率 100%」是恒真指标**（引用由检索结果机械生成），不构成质量证据。

## 六、ETL 缺陷：表格形式的【处方】被整张丢弃（530 个成方制剂）

修完上面 4 个检索缺陷后，回头追"51 个成方制剂被错标为药材和饮片"这条，发现根因严重得多。

### 现象

`_infer_category` 靠"有【处方】/【规格】"判成方制剂、靠"有【来源】/【性味与归经】"判药材，
两边都不命中就落到**兜底 `return "药材和饮片"`**。而这些被误标的条目**全都没有【处方】章节**。

### 根因

成方制剂的【处方】在 .docx 里是**表格**形式，首格形如「【处方】醋香附138g」，
且该表**紧跟拼音名之后**——此时解析器的 `current_section` 仍是 `None`。
而表格处理分支是：

```python
elif btype == 'table':
    if current_section:          # ← None → 整张表被静默丢弃
        ...attach table_markdown...
```

于是【处方】既没成为章节、内容也没进 `intro_text`，**凭空消失**。

### 量化

| 指标 | 数值 |
|------|------|
| 全文首格带【章节】标记的表格 | **556 张，全部是【处方】** |
| 其中 drugs.json 里**没有**处方章节（内容丢失） | **530 个成方制剂** |
| 这些条目的分类 | 472 已正确、**58 被误判为"药材和饮片"** |

对药典问答系统这是**功能缺失**：530 个成方制剂答不出"XX丸的处方是什么"。

### 修复

表格首格若匹配到【章节】标记，就以该标记**开一个新章节**（整表转 Markdown 作为内容）：

```python
head = block.rows[0].cells[0].text.strip()
head_match = SECTION_PATTERN.match(head)
if head_match:
    if current_section: entry.sections.append(current_section)
    current_section = Section(section_name=head_match.group(1).strip(),
                              content=table_md, table_markdown=table_md, raw_paragraphs=[head])
elif current_section:
    ...原有逻辑...
```

**一处修复两处受益**：`_infer_category` 的 `'处方' in section_names` 随之命中，
分类错标**自愈**——不必去动那个有 103 条分歧的启发式规则（见下"遗留"）。

### 修复效果（重跑 ETL + 重建两套索引后）

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 含【处方】章节的条目 | 908 | **1395** |
| 切片总数 | 11,369 | **11,990** |
| `category=成方制剂和单味制剂` 的切片 | 8,013 | **8,860** |
| 手撕版 strict Hit@5（基线 100 题） | 85.39% | **87.64%** |
| 标准版 strict Hit@5（基线 100 题） | 83.15% | **84.27%** |

> 注意：`drugs.json` 的条目数没变（2387），说明这不是"多解析出条目"，而是**原本就存在的条目恢复了内容**。

### 配套的工程改动

- 新增 `tests/test_etl_parser.py`（5 项，**合成 docx**，不依赖受版权保护的药典原文件）
- 历史基线回归测试改用固化 fixture `tests/fixtures/baseline_chunks.json`：
  基线重算需要 chunk 完整正文，若直接读 `chunks.json`，一旦重跑 ETL 就会"因数据变化而失败"，
  失去防口径漂移的意义。fixture 只含基线报告用到的 310 个 chunk（382 KB）。

## 七、分类判定改为「按大类标题」（原启发式降级为回退）

药典一部按 **药材和饮片 → 植物油脂和提取物 → 成方制剂和单味制剂** 的顺序编排，
文档里也确实存在后两个大类标题，因此按大类标题推进分类是**权威**判据，
比"数章节特征"的启发式可靠得多。

### 实现

1. `MAJOR_CATEGORY_HEADINGS` 常量 + `self._current_category` 状态（默认"药材和饮片"，
   因为"药材和饮片"标题未必以独立段落出现）
2. 外层 `parse()` 循环遇到大类标题时切换分类并跳过；
   文档完全没有大类标题时（如合成测试文档）`_saw_category_heading=False`，回退到 `_infer_category`
3. ⚠️ **踩坑**：`_is_entry_boundary` 不会把大类标题当边界（它在 `SECTION_HEADER_KEYWORDS`
   里被显式排除，以免被误认成药品名），于是 `_parse_drug_entry` 的内层循环会把标题
   **当正文吞掉**，外层永远看不到 → 必须在内层循环里显式 `break` 交回外层。
   第一次实现就踩了这个坑（验证时发现 `肉桂油` 分类没变才暴露）。

### 实测变化：41 条（不是先前估的 103）

先前用 `para_start` 与 block 序号比较，**两个索引空间不同源**，得出的 103 条不可信；
实现后用段落名对齐重算，真实变化 **41 条**：

| 变化方向 | 条数 | 样例（均为正确修正） |
|---|---|---|
| 药材和饮片 → 植物油脂和提取物 | 23 | 丁香罗勒油、八角茴香油、肉桂油、松节油、薄荷脑、灯盏花素、黄藤素… |
| 成方制剂 → 植物油脂和提取物 | 1 | 肿节风浸膏 |
| 药材和饮片 → 成方制剂和单味制剂 | 17 | 十二味翼首散、四逆汤、藿香正气水、如意金黄散、华佗再造丸… |

切片层面的分布：植物油脂和提取物 71 → **163** 片。

### ⚠️ 效果说明：正确性改进，但当前评测集**几乎测不出来**

重跑 ETL + 重建两套索引后复测，**各项指标精确到小数点后完全相同**（src 88.42% / lc 85.26%）。
逐题对比显示全 106 题里**只有 1 题**（Q066「哪些药材含有挥发油成分？」）的召回顺序发生变化，
而 Q066 本身还是 11 道不可评测题之一。

原因是这 41 条都落在测试集从未命中的位置。所以：

- **该改动的价值是数据正确性**（"植物油脂和提取物"这一类目现在可被正确检索；
  "哪些药材/中成药"的过滤不再混入错误类目），
- **不是指标提升**，不要把它当作评分依据。

这又一次说明当前 106 题评测集对"类目/数据质量类"改动是盲的——与缺陷 3
（子串扩展 0/106 覆盖）是同一现象。
